 ### P2-1: Source-level vs bytecode-level attestation
 inconsistency (should fix)

 _runtime_implementation_fields (h_campaign.py)
 attests OpenAICompatWorker and
 parse_output/strip_think via
 _class_projection/_callable_projection (bytecode:
 co_code, co_consts, co_names, etc.), but attests
 MemoryAwareRunner, MemoryActionBroker,
 deterministic_verify,
 _actual_contains_secret_material,
 _resolve_indexed_record, and case_input_digest via
 _implementation_digest (inspect.getsource — source
 text only). A __code__-level swap on any
 source-attested function would not change its source
 digest, so the runtime guard would not detect it.
 The verify path catches the behavioral consequence
 (verdict re-derivation, advice-chain checks) in a
 fresh process, but the runtime guard itself is
 bypassable for these functions. Worker/parser are
 not vulnerable (bytecode-attested). Recommend using
 _callable_projection/_class_projection for
 wrapper/broker/evaluator/resolver for consistency.

 ### P2-2: Transitive attestation gap for
 assert_secret_safe (should fix)

 _actual_contains_secret_material (h_campaign.py)
 imports and calls assert_secret_safe from
 metaharness.portable.integrity. The evaluator digest
 attests _actual_contains_secret_material's source
 (which contains the import statement as text) and
 the inline _SECRET_FRAGMENT regex, but not the
 implementation of assert_secret_safe itself. If
 assert_secret_safe is neutralized (e.g., patched to
 never raise), the source digest of
 _actual_contains_secret_material is unchanged, but
 the canonical scanner path is disabled. The
 _SECRET_FRAGMENT regex still catches key=value-style
 credentials, but secrets not matching that pattern
 could leak through the verifier. Recommend
 transitively attesting assert_secret_safe (and
 PortableIntegrityError) into the evaluator digest,
 or restricting the scanner to only inline logic.

 ### P2-3: Seed probe uses dummy task, not actual
 task (should fix)

 _enforce_runner_model_contract (h_campaign.py)
 probes
 inner._body(Task(id="model-contract-seed-probe", …),
 [], []) to assert request_body["seed"] == seed. This
 is a proxy: the actual outbound request body (for
 the real task with advice injected) is not retained
 in evidence, and the probe uses a different task. A
 worker whose _body conditionally drops the seed
 based on task content could pass the dummy probe but
 drop the seed for the actual task. The worker's
 bytecode is attested (catching code-level
 modifications), and the committed spec binds to that
 bytecode, but the actual request body is not
 independently verifiable on reload. Recommend
 probing with the actual task (after task is
 constructed) or retaining the actual request body
 digest in evidence.

 ### P2-4: Validation approval does not enforce
 advice-chain load-bearing (should fix)

 _development_selection_eligible calls
 _enforce_advice_chain_load_bearing, which raises if
 optimized advice is byte-identical to base
 (preventing false attribution). But
 _validation_approved_pairs (h_campaign.py) only
 checks base-fail → optimized-pass for
 approved-target cases, without asserting
 advice_digest/inner_task_digest differ. With
 temperature=0.0 and seed pinned, identical advice
 should yield identical verdicts, so base-fail →
 optimized-pass implies advice differs — but this
 relies on model determinism rather than enforcing
 it. If the model has residual non-determinism
 (batching, GPU variance), a validation
 approved-target case could show base-fail →
 optimized-pass with identical advice, producing a
 false eligible verdict. The development selection is
 robust to this; validation is not. Recommend
 extending the advice-chain check to validation
 approved-target pairs.

 ### P3-1: _digest vs canonical_json_bytes
 serialization fragility

 MemoryAwareRunner._digest (memory.py) uses
 json.dumps(…, separators=(",",":"), sort_keys=True,
 ensure_ascii=False, default=str), while the campaign
 uses canonical_json_bytes from
 metaharness.portable.integrity. The verify path
 recomputes
 outer_task_digest/inner_task_digest/advice_digest
 via canonical_json_bytes and compares to the
 wrapper's _digest-based values. If the two
 serializations ever diverge (e.g., ensure_ascii or
 default behavior), verify would fail. Recommend
 using canonical_json_bytes in the wrapper for
 consistency.

 ### P3-2: _code_projection omits Python 3.11+ code
 attributes

 _code_projection (h_campaign.py) captures co_code,
 co_consts, co_names, co_varnames, co_freevars,
 co_cellvars, co_flags, co_argcount,
 co_posonlyargcount, co_kwonlyargcount. It does not
 capture co_exceptiontable, co_qualname, or
 co_linetable (3.11+). These could theoretically
 differ without changing the captured projection.
 Minor gap for bytecode-level attestation.

 ### P3-3: _callable_projection uses repr() for
 defaults

 _callable_projection (h_campaign.py) captures
 __defaults__ and __kwdefaults__ via repr(). For most
 defaults (None, int, str, bool) this is
 deterministic, but for mutable or custom objects
 repr may not capture full state. Minor.

 ### P3-4: _assert_secret_safe_worker_result called

 ### P3-5: case_set_digest does not bind actual case

**P1-1 — Stale W / task-model portfolio reference contradicts the resume mandate and the frozen H model.**
`.agents/meta34-campaign-spec.json` commits `task_model_portfolio_ref: "portfolio-qwen3-5-35b-a3b-coding-nvfp4"` (references the *retired* 35b model) while `model.model_id: "qwen3.5:4b"` and `model.model_digest: "sha256:2a654d98e6fba55d452b7043684e9b57a947e393bbffa62485a7aac05ee4eefd"`. `w_refs[0]` equals `task_model_portfolio_digest` (`sha256:6e73b30f…`), so the frozen W axis attests a portfolio whose human-readable binding still names the 35b model the resume explicitly ordered replaced (`.agents/meta34r-definition.json` budget: "replacing the retired qwen3.5:35b-a3b-coding-nvfp4 pin"). In `CampaignSpec._populate_frozen_axes` (h_campaign.py) `task_model_portfolio_digest` defaults to `self.model.model_digest` *only when empty*; when supplied it is trusted verbatim, and no validator enforces that `task_model_portfolio_ref`/`digest` correspond to `model.model_id`/`model_digest`. `CampaignSpec._contract` validates `w_refs` only for non-emptiness, uniqueness, and hash shape. It never asserts that `w_refs` contains `task_model_portfolio_digest` or relates to `model.model_digest`. Combined with P1-1, the W axis can carry an opaque digest that disagrees with the actual task model without tripping any spec guard.

**P3-2 — Holdout ledger is burned before package validation succeeds.**
`load_protected_inputs` consumes the O_EXCL ledger, then reads and validates the package. Ordering is correct per the "never opened before ledger consume" invariant, but a malformed/digest-mismatched holdout package permanently consumes the one-shot slot with no retry. ## Findings (chunk C2)

### P1

**1. Holdout ledger consumed before protected-verdict re-derivation; contract failure after consumption leaves no verdict and no retry.**
In `_run_ordered_campaign`, step 3 calls `load_protected_inputs(holdout_input_path, …, ledger=ledger)` (O_EXCL consume), then step 4 re-derives the protected verdict via `_ablation_campaign_for_split` and `_rederive_protected_result` before `_persist_ablation_result`. `_ablation_campaign_for_split` raises `CampaignContractError` when `optimized_snapshot.parent_snapshot_hash != base_snapshot.content_hash`, and `_rederive_protected_result` calls `evaluate_protected_h_ablation`/`PromotionGate().decide` which can also raise. If any of those raises after the ledger claim, the function exits with an exception: `holdout_ledger_key` is bound, the ledger is consumed, but no terminal `result.json`/`manifest.json` is written. A retry re-enters `load_protected_inputs` and hits `HoldoutAlreadyConsumedError`. The "consumed exactly once" invariant therefore does not guarantee a recorded verdict — the holdout can be burned with no terminal artifact and no eligible/ineligible result, violating bounded authority + sealed-holdout post-condition.

### P2

**2. `case_set_digest` does not bind the case set it claims to attest.**
`_build_protected_manifests` sets `"case_set_digest": sha256_hex((split + ":" + spec.campaign_id).encode("utf-8"))`. This hashes only `split` and `campaign_id`; it omits case IDs, input digests, mandatory flags, and view membership. Two different case sets for the same campaign/split yield identical digests, so the manifest field named `case_set_digest` attests nothing about the actual case set. (Case membership is checked elsewhere in `_phase_execution`/`_validate_package`, but the tamper-evident manifest does not bind it.)

**3. Evaluator implementation digest omits callee implementations and attests secret-scan kinds by name only.**
`_runtime_implementation_fields` builds `deterministic_evaluator_implementation_digest` from `_implementation_digest(deterministic_verify)` and `_implementation_digest(_actual_contains_secret_material)` — both via `inspect.getsource`, which captures only the function's own source text, not the implementations of helpers they call. `_SECRET_SCAN_KINDS` is reduced to `f"{kind.__module__}.{kind.__qualname__}"` strings, so changing a scanner class body without changing its qualname leaves the digest unchanged. The "recursive secret scan bound into the evaluator digest" claim is therefore only partially attested; a swapped helper or scanner implementation can evade the guard.

**4. Seed probe checks `inner._body` with a synthetic Task, not the actual `runner.run` execution path.**
In `_enforce_runner_model_contract`, the per-attempt seed is validated by calling `inner._body(Task(id="model-contract-seed-probe", …), [], [])` and checking `request_body.get("seed") == seed`. The real attempt is produced by `runner.run(task)`; if `MemoryAwareRunner.run` mutates `inner.extra_body`, builds the request through a different method, or strips/re-adds the seed, the probe (which bypasses `run` and uses a dummy task) would still pass while the actual outbound body drifts. The attestation covers `_body`'s contract, not the live outbound request body emitted during execution.

**5. Secret-safety screen covers only `worker_result_dump`, not the full evidence row.**
`_phase_execution` calls `_assert_secret_safe_worker_result(worker_result_dump)` before persisting, but the same row also stores `outer_task`, `inner_task`, `selected_record_contents` (with full `content`), `consult_receipt_before_content_hashes`, etc., drawn from `runner.last_evidence`. None of those fields pass through `assert_secret_safe`. If a selected memory record or inner-task payload contains secret-like material, it is written to `evidence.json` unscreened, breaching the "fail closed before raw text reaches evidence" intent.

**6. `load_spec` requires `spec_digest` to be present but does not verify it matches the recomputed digest.**
`load_spec` only checks that `raw["spec_digest"]` is a non-empty string, then `CampaignSpec.model_validate(raw)`. It never compares `raw["spec_digest"]` to `spec.digest()`. Terminals later use `spec.digest()` (recomputed), so a file with a stale/forged `spec_digest` loads successfully; the precommitted digest is a required field, not a verified binding. A spec could be tampered after pinning and still load unless a separate guard checks the recomputed value.

**7. `_build_protected_rows` silently drops cases without exactly three cell bindings.**
`if len(bindings) != 3: continue` skips building a `ProtectedEvidenceRow` for any (view, case_id) missing a cell, instead of raising. If an attempt row is absent for one cell (e.g., a memory cell produced no rows, or a view/case filtering bug), the case vanishes from protected evidence with no error, masking the asymmetry rather than failing closed.

**8. `_persist_ablation_result` writes `result_store.create` before the O_EXCL evidence files; partial-write leaves a stored result unbound by evidence/manifest.**
`_persist_ablation_result` calls `result_store.create(protected_result)` first, then `_create_only_json(evidence_root / "evidence.json", …)`, `result.json`, `manifest.json`. If any `_create_only_json` raises `FileExistsError` (e.g., a prior partial run left `evidence.json`), the protected result is already persisted but the manifest that binds `protected_result_id`/`protected_result_digest` to the evidence digest is never written. The stored result is then unbound on reload.

### P3

**9. Task schema attestation covers field names only.**
`_runtime_implementation_fields` uses `"task_schema": tuple(Task.model_fields)`, which is the field-name keys; field types, defaults, and constraints are not attested. A type/default change on an existing field leaves the digest unchanged.

**10. `_class_projection` attests only own methods, not inherited ones.**
`_class_projection` iterates `value.__dict__.items()`, so methods inherited by `OpenAICompatWorker` from `BaseRunner` are excluded unless separately projected (only `BaseRunner.run` is). Changes to other inherited methods evade the worker attestation.

**11. Per-attempt budget envelope equals the total budget, and totals are enforced per cell.**
`_enforce_per_attempt_budget` and `_enforce_total_budget` both read `spec.budget`; `_enforce_total_budget(spec, total_metrics[cell])` is invoked once per cell. A single attempt can therefore consume the full envelope, and the campaign aggregate can reach 3× the frozen budget. Conservative, but if a per-attempt cap was intended, this is wrong.

**12. `_create_only_json` does not harden parent directory mode.**
`path.parent.mkdir(parents=True, exist_ok=True)` uses the process umask; the file is `0o600` but the evidence directory may be group/world-readable. Minor hardening gap.

**13. Test-only non-tool posture check is name-based.**
`_enforce_runner_model_contract` uses `type(inner).__name__ == "OpenAICompatWorker"` (string match) for the canonical non-tool posture checks, bypassable by a same-named class in the test-only path. Production is mitigated by the identity check `type(runner.inner) is local_module.OpenAICompatWorker`.

**14. `_enforce_advice_chain_load_bearing` raises without persisting development evidence.**
The load-bearing guard raises `CampaignContractError` from inside `_development_selection_eligible`, propagating out of `_run_ordered_campaign` before any `_store_terminal` call. The development rows are never persisted, so a contract failure in the development phase leaves no terminal verdict and no evidence for forensics (acceptable as fail-closed, but defeats full-fidelity evidence for that failure mode).

```python
    for cell in exact.cells if cell.name == "base_scaffold"
)
optimized_snapshot = next(
    cell.optimized_snapshot
    for cell in exact.cells if cell.name == "optimized_scaffold"
)
if base_snapshot is None or optimized_snapshot is None:
    raise CampaignContractError("frozen validation ablation snapshots are missing")
```
If either cell is absent, `next` raises `StopIteration` before the `None` check runs, surfacing as a bare `StopIteration` rather than the file's `CampaignContractError` contract. Spec-digest validation likely prevents this in practice, but the defensive `None` check is dead code as written. Use `next(..., None)`.

### P3 — Before-hash validation chain unexercised by campaign-level verdict tests

**`tests/test_real_h_campaign.py` — `_MakeReceiptBroker`.**
`_MakeReceiptBroker` (used by `_verdict_factory` for all campaign-level verdict tests) returns `before_content_hashes=()`:
```python
before_content_hashes=(),
```
So the `supplied_hash`/`current_hash` mismatch branch in `MemoryAwareRunner._consult` is never hit by the verdict factory tests. Only `_broker_with_record` (wrapper unit tests) populates `before_hashes`. The before-hash chain — a load-bearing integrity check for tampered record content between consult and resolve — has no campaign-level positive/negative test.

### P3 — Factory ignores the `config`/`runner_config` parameter

**`h_campaign.py` production `factory` and `tests/test_real_h_campaign.py` `_verdict_factory`.**
Both factories accept a `config`/`runner_config` argument but rebuild the worker from `exact`/`seed` directly:
```python
def factory(cell, repetition, seed, config: dict[str, Any]) -> MemoryAwareRunner:
    inner = OpenAICompatWorker(
        ..., extra_body={**(exact.model.inference_parameters.get("extra_body") or {}), "seed": seed},
    )
```
The evidence stores `runner_config` via `_build_worker_config(exact, cell, repetition, seed)`. Since both derive from `exact`, they agree today, but the passed `config` is silently discarded. If the campaign ever transforms `config` before passing it (e.g., per-cell overrides), the runner and the evidence would diverge without a guard. The parameter should either be used or removed.
